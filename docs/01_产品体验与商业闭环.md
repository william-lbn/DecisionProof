# 产品体验与商业闭环

## 1. 目标客户

首批客户应满足：使用 GitLab Self-Managed、Kubernetes，研发团队 50—500 人，正在引入 AI Coding Agent，并且存在安全、审计或发布失败成本。

优先行业：金融、制造、能源、运营商、政企、医疗软件、云平台和企业基础软件。

## 2. 角色工作台

### 产品经理

- 上传或连接 Word/PPT/会议纪要；
- 查看 AI 提取结果和来源页码/段落；
- 处理矛盾、缺失项和低置信度内容；
- 批准目标、需求、验收标准和 Outcome Contract；
- 查看上线后的业务结果。

### 架构师

- 查看工程就绪包；
- 评审方案、ADR、API/数据兼容、威胁模型和回滚；
- 对架构摘要签名批准；
- 查看架构决策是否被代码和制品实现。

### 研发与 Agent

- 从 GitLab Issue 和工程基线接收任务；
- 在隔离 Workspace 中修改代码；
- 输出结构化 Tool Call、测试结果、Commit 和 Patch Digest；
- 创建 Draft MR，不得直接合并。

### 发布/SRE

- 查看 Release Evidence Manifest；
- 处理待批准发布；
- 观察 Canary、No Data、自动回滚；
- 完成 Outcome 验证和复盘。

## 3. 易用性设计

平台不能要求产品经理先学习 YAML、Git 或 OpenSpec。第一入口是拖拽现有资料。平台应自动展示：

- 项目目标；
- 需求；
- 验收条件；
- 风险；
- 约束；
- 非范围；
- 架构假设；
- 业务指标；
- 来源位置；
- 矛盾和缺失项。

每条提取结果必须支持：接受、修改、拒绝、查看来源、指派 Owner、发起评审。

## 4. 商业价值

客户长期付费的理由不是“AI 会写 PRD”，而是：

- 防止 PPT/Word 中的承诺在研发中丢失；
- 防止 Agent 越权和未经验证的代码进入生产；
- 自动形成合规和审计证据；
- 降低发布失败、重复副作用和错误灰度风险；
- 发现“上线了但没有业务价值”的项目；
- 保留客户已有工具，降低迁移成本。

## 5. 商业版本建议

- Community：单 GitLab、单集群、基础文档输入、基础证据链；
- Team：多项目、Agent、CI 证据、Release Manifest、Argo Rollouts；
- Enterprise：HA、SSO、KMS、高级策略、审计、灾备、私有模型、连接器和服务支持。

计价更适合按受管研发人员、受管服务和年度企业许可，而不是按模型 Token 转售。

## 6. 商业闭环指标

平台自身需要跟踪：

- 项目接入时间；
- Engineering Readiness Lead Time；
- Agent 任务成功率；
- MR 人工返工率；
- 缺失证据阻断率；
- 发布失败率；
- 回滚时间；
- Requirement-to-Deployment 可追踪率；
- Outcome Verified 比例；
- 审计准备时间；
- 客户续费和扩展服务数。
